# Модель данных

Система использует SQLite. Физически баз две:

| База | Файл | Кто пишет | Назначение |
|---|---|---|---|
| Платформа | `db/combat.db` | платформа :3000 | заявки, пользователи, документы, ЭДО, журнал, **все таблицы `Dispatch*`** |
| Модуль водителя | `driver/db/custom.db` | модуль :3102 | рейс водителя, точки, события, чат, журнал синхронизации |

Схемы описаны в `prisma/schema.prisma` (платформа), `prisma/kontur.prisma`
(диспетчерская, префикс `Dispatch`) и `driver/prisma/schema.prisma` (водитель).
Файлы баз и `upload/` не коммитятся: в git только схемы и демо-данные модуля.

## 1. Платформа (`prisma/schema.prisma`)

### 1.1. Пользователи и доступ

| Модель | Смысл | Ключевые поля |
|---|---|---|
| `User` | учётная запись | `login`, `passwordHash` (scrypt), `role` (`admin`/`logist`/`carrier`), `carrierId`, `profile` |
| `Profile` | профиль пользователя | ФИО, телефон, должность |
| `AccessTemplate`, `TemplatePerm`, `PermException`, `RolePerm` | шаблоны и исключения прав | `section:*`, `own:*` |
| `Carrier` | перевозчик/экспедитор | ИНН, КПП, ОГРН, контакты, `role` (`CARRIER`/`EXPEDITOR`), рейтинг |
| `Notification` | уведомления | адресат, тип, прочитано |

Пароли хранятся только как scrypt-хеш. Сессия — подписанная HttpOnly-кука
(плюс Bearer для API). Права проверяются на сервере в каждом маршруте, не
только в интерфейсе.

### 1.2. Справочники

`Driver` (водитель), `Truck` (ТС), `Trailer` (прицеп), `DirectoryPhoto`,
`CargoType` (груз). Справочники общие для платформы и «Контура»; у водителя
есть `carrierId`, у ТС — тип кузова, тоннаж, госномер.

### 1.3. Заявки и торги

| Модель | Смысл |
|---|---|
| `Request` | заявка на перевозку: маршрут, груз, тоннаж, тип ТС, даты, ставка, режим (`FIXED`/`AUCTION`/`CLOSED`), статус, `onecRef` |
| `Bid` | ставка перевозчика (цена за тонну/рейс, время) |
| `Ticket`, `TicketMessage`, `TicketAttachment` | обращения в поддержку и переписка |
| `RequestFile` | файлы заявки (ТЗ, схемы, фото груза) |
| `Document` | документы исполнителя: паспорт, регистрация, ВУ, СТС, М-2; `dataUri`, поля, уверенности, вердикт |
| `Event` | журнал бизнес-событий заявки |
| `PlatformLog` | технический журнал действий |
| `Setting` | настройки платформы |

Жизненный цикл `Request.status`:

```
DRAFT → PUBLISHED → AWARDED → DOCS_REVIEW → AT_LOGIST → CONFIRMED → CLOSED
                         └── QUARANTINE / DELETED
```

`Request.onecRef` — уникальный ключ документа 1С («номер от даты»), защищает
от дублей при повторной отправке.

### 1.4. ЭДО

`EdoDocument` — ЭТрН и связанные титулы, `DiadocState` — ротированный
refresh-токен и служебное состояние интеграции. Сами подписанные документы
хранятся в Диадоке; в платформе — идентификаторы, статусы и метаданные.

## 2. Диспетчерская (`prisma/kontur.prisma`, префикс `Dispatch`)

| Модель | Смысл |
|---|---|
| `User` | отдельная учётка «Контура» (логист/админ) |
| `Driver`, `Vehicle`, `Trailer` | собственный парк |
| `Order` | заявка из 1С/ATI.SU/вручную, статус, внешний ключ |
| `Trip` | рейс: водитель, ТС, прицеп, статус, план/факт |
| `Leg` | плечо рейса: погрузка/выгрузка, адреса, окна, **геометрия маршрута** |
| `StatusEvent`, `TripEvent` | события заявки и рейса |
| `DriverOnline`, `DriverGeoPoint` | онлайн-статус и GPS-треки |
| `Device` | привязка устройства/APK к водителю |
| `FileRec` | файлы «Контура» |
| `Outbox1c` | очередь исходящих событий в 1С |
| `CallTask` | задания на звонки |
| `VehicleBinding` | связка водитель ↔ ТС |
| `AtiDeal` | сделки ATI.SU |
| `PlanEntry` | планирование занятости |
| `AuditLog` | аудит действий диспетчерской |

Ключевые поля маршрута в `Leg`:

- `routeGeometry` — GeoJSON `LineString` с координатами `[lng, lat]`;
- `routeWaypoints` — JSON-массив точек `{lat,lng}` в порядке объезда;
- `routeDistanceM`, `routeDurationS` — метры и секунды;
- `routeSource` — `yandex` или `osrm`;
- `routeLink` — исходная ссылка Яндекс.Карт.

## 3. Модуль водителя (`driver/prisma/schema.prisma`)

| Модель | Смысл |
|---|---|
| `Trip` | снимок рейса для водителя: код, статус, адреса, ТС, геометрия, точки, ETA |
| `TripPoint` | точка рейса (погрузка/выгрузка/остановка), порядок, статус |
| `TripEvent` | событие рейса (выезд, погрузка, выгрузка, завершение) |
| `RoadMark` | дорожная пометка водителя (ремонт, пост, пробка) |
| `MarkVote` | подтверждение/опровержение пометки другими водителями |
| `MarkPublicationLog` | публикация пометки, защита от спама |
| `ChatMessage` | чат водителя с офисом |
| `SystemNote` | системные сообщения |
| `SyncJournal` | журнал изменений: `seq`, `entity`, `op`, `payload`, `createdAt` |
| `SyncOperation` | идемпотентность входящих операций по `opId` |

`SyncJournal.seq` — курсор клиента. Клиент присылает `cursor=N`, получает
записи `seq > N`, применяет пачку и только потом сдвигает курсор. Повторная
операция с тем же `opId` не применяется второй раз.

## 4. Согласованность

- Платформа — источник истины по заявкам, правам и деньгам.
- «Контур» пишет только свои `Dispatch*`-таблицы в той же `combat.db`.
- Модуль водителя получает снимок рейса через `driver-bridge.ts`; его база
  независима и переживает пересборку платформы.
- Внешние ключи 1С — `external_id`/`onecRef`; обмен идемпотентен.
- Удаление заявки — мягкое (`DELETED`), история и документы сохраняются.

## 5. Миграции и резервные копии

```powershell
npm run db:push        # применить схему платформы (Prisma db push)
npm run db:generate    # сгенерировать клиентов
npm run auth:seed      # учётные записи
```

Для модуля водителя — `cd driver; npx prisma db push`. Перед обновлением
схемы сделайте копию `db/combat.db` (см.
[../operations/backup-restore.md](../operations/backup-restore.md)).
