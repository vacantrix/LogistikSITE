# Аудит №3 — 30.10.2026: «теряется соединение и восстанавливается» + продолжение поиска ошибок

Повод: пользователь замечает периодическую потерю соединения с быстрым восстановлением; просит выяснить
причину, наличие бага и продолжить аудит ошибок.

## 1. Причина наблюдаемого поведения (это НЕ сбой — так и задумано)
Оверлей «Восстанавливаем соединение» (page.tsx, Task 52) появляется при обрыве сокета после успешного
подключения и исчезает при reconnect. Клиент переподключается сам (1–3 с), плюс платформа продолжает
работать на автообновлении раз в 15 с. Источники кратковременных обрывов на стенде:
1. **Пересборки dev-режима.** Любая правка кода → Turbopack HMR/Fast Refresh → сокет переподключается
   (в консоли видно «Fast Refresh rebuilding»). В production-режиме этого нет.
2. **Чурн предпросмотров песочницы** — скрытые iframe-предпросмотры открываются/закрываются, каждое
   открытие = новое WS-подключение (в логе шины: пики подключений при правках).
3. Рестарт самого ws-сервиса (`bun --hot`) при правках его кода — все клиенты переподключаются разом.
Вывод: поведение штатное, самовосстанавливающееся; данные при этом не теряются (перезачитываются через API).

## 2. Найдены и ИСПРАВЛЕНЫ реальные баги инфраструктуры real-time
1. **ГЛАВНЫЙ: шина была запущена двумя процессами** (супервайзер песочницы стартовал её дважды 29.10):
   PID-A держал :3004 (/notify — приём событий от платформы), PID-B держал :3003 (браузеры). События
   platform:update уходили в процесс А, у которого сокет-сервер был без клиентов — **реал-тайм события
   не доходили до браузеров вообще**; всё «работало» только на 15-секундном опросе. Исправлено: дубли
   остановлены, поднят один экземпляр, держащий ОБА порта; сквозная проверка `POST /notify` →
   `broadcast AUDIT_PING → 2 client(s)` — события доходят до подключённых браузеров.
2. **Шина работала без проверки входа**: ws-service не получал `AUTH_SECRET` (скрипт `dev` не загружал
   общий .env) — в логе было «AUTH_SECRET не задан», allowRequest пропускал всех. Противоречие с README
   («пускает только с валидной сессией»). Исправлено: `bun --hot --env-file=../../.env index.ts`
   (+ согласованы node-варианты запуска в package.json ws-сервиса и корневом `npm run ws`);
   предупреждение исчезло, авторизация реально включена. Инструкция в mini-services/ws-service/README.md
   дополнена признаками корректного запуска (без строки про AUTH_SECRET; оба порта — один процесс).
3. **Вечный оверлей при недействительной сессии**: `reconnectionAttempts: Infinity` + ответ шины
   «unauthorized» = бесконечный цикл с оверлеем «Восстанавливаем соединение» навсегда. Исправлено
   (page.tsx): при connect_error с unauthorized — остановить переподключение и вернуть на экран входа
   тем же механизмом, что и 401 от API (UNAUTHORIZED_EVENT).
4. **Наблюдаемость**: в лог шины добавлены временные метки ISO и причина disconnect (`reason=…`) —
   раньше сопоставить обрывы с событиями платформы было невозможно.

## 3. Проверено и опровергнуто / не критично
1. **254–257 «online» в логе** — накопленные за ~19 часов сокеты скрытых iframe-предпросмотров и старых
   сессий (220 подключений против 64 отключений). Не утечка платформы: движок сам дожимает мёртвых
   (pingTimeout 60 с), часть сокетов реально жива в скрытых предпросмотрах. После чистого рестарта
   счётчик обнулился. Для стенда не критично; перезапуск шины лечит.
2. **5×401 в dev.log** — штатные `/api/auth/me` и `/api/settings` при открытии сайта без входа; не баг.
3. **EADDRINUSE в логе ocr-service** — артефакт дублированного старта; действующий экземпляр здоров
   (uptime 3,5 ч, обработано 4 запроса, /health отвечает). Шлюз :3020 работает.
4. **Локальный paddle-ocr не стартует** (`.venv/bin/python: No such file or directory`) — ожидаемо:
   нейросеть крутится на отдельном стенде АЭМЗ, локальный движок в этой песочнице не развёрнут;
   на маршрут платформы не влияет.
5. **Разовый отказ dev-сервера ~08:23** — процесс Next dev исчез без следов в логе (последние записи —
   успешные 200; памяти достаточно, 3 ГБ свободно). Поднят заново тем же способом, WS-клиенты
   переподключились за ~1 с (в новом логе шины видно: «reason=transport close» → connected). Наблюдение
   зафиксировано как особенность песочницы; действий, кроме перезапуска, не требуется.
6. **TTL сессии 7 дней** — во время просмотра не истекает; токен WS проверяет подпись и exp, но НЕ
   версию сессии `sv` (logout в другой вкладке не убивает WS до истечения exp). Известное ограничение:
   ws-сервису нужна БД для проверки sv — не делаем на стенде, зафиксировано здесь.

## 5. Дополнение (вторая сессия аудита №3, тот же день): живой эксперимент и новый исправленный баг
Независимая перепроверка всех выводов секций 1–3 по свежим логам — подтверждено (один процесс шины
держит оба порта, AUTH_SECRET подхвачен, предупреждений нет, таймстемпы пишутся). Новое:

### 5.1. Живой эксперимент: полный цикл «обрыв → восстановление» воспроизведён
Браузер (logist1, через шлюз :81 — как реальный пользователь) → SIGTERM ws-service:
- оверлей «Восстанавливаем соединение» появился через ~1 с (wasConnected → connLost) — **именно то,
  что наблюдает пользователь**;
- сервис был поднят заново вручную → клиент переподключился автоматически за 1–2 с
  (в логе шины: `client connected … (online: 1)`), оверлей исчез, консоль чиста, данные на месте.
- Уточнение к п.1: Fast Refresh (правки компонентов) сокет НЕ рвёт — во время двух пересборок
  соединение жило. Обрыв дают только рестарты процессов (Next dev, ws-service) и полные
  перезагрузки страницы, плюс, вероятно, троттлинг фоновой вкладки браузера и внешний
  прокси-туннель превью (изнутри песочницы непроверяемо — но симптом у них тот же и восстановление
  такое же автоматическое).

### 5.2. НОВЫЙ БАГ — исправлен: блокирующий оверлей при долгом простое шины
Во время эксперимента шина лежала ~1,5 минуты — и оверлей `fixed inset-0 z-[100]` всё это время
**полностью блокировал интерфейс**, хотя Next.js и HTTP-автообновление (15–30 с) работали: данные
грузились, а работать было нельзя и закрыть оверлей было нечем. Исправлено (page.tsx): первые 8 секунд —
прежний оверлей (штатный рестарт укладывается в 1–3 с), при долгом простое — неблокирующий янтарный
баннер сверху «Нет связи с шиной реального времени» с кнопкой «Продолжить работу». Проверено живо:
под баннером навигация работает, при reconnect баннер исчезает сам. `bun run lint` и tsc — чисто
(первый вариант с setState в effect отклонён линтером `react-hooks/set-state-in-effect` — переписан
на паттерн «adjust state when props change»).

### 5.3. НОВОЕ — задокументировано: у мини-сервисов НЕТ автосупервизора
SIGTERM/падение ws-service = сервис лежит, пока не поднять вручную (сигнатура «error: script "dev"
was terminated by signal SIGTERM» в логе без следующего старта). Прошлые «самопроизвольные» рестарты
в логе — это ручные подъёмы, не супервизор. Штатная команда перезапуска (double-fork, scripts/
daemonize.py) добавлена в mini-services/ws-service/README.md вместе с двумя подводными камнями:
- `bun --hot` НЕ применяет правки `index.ts` к работающему серверу: новый экземпляр падает
  EADDRINUSE, старый продолжает работать на прежнем коде (видно в логе шины) — после правок нужен
  полный рестарт;
- при доступе к платформе МИМО шлюза (:3000 напрямую) WS-рукопожатие получает HTML страницы вместо
  engine.io-ответа — клиент молча крутит ретраи без единого сообщения в консоли. Через шлюз
  (`/?XTransformPort=3003`, как в превью) подключение мгновенное. Честная оговорка: диагностировать
  такой «тихий» случай неудобно, но production-схема (шлюз или NEXT_PUBLIC_WS_URL) от этого не страдает.

### 5.4. Журнал ошибок (PlatformLog) и смежные проверки

# Аудит №4 — 30.10.2026: матрица доступа (IDOR) и смежные проверки безопасности

Повод: «где ещё не смотрели» — по всем 46 API-роутам построена матрица авторизации (обзор по всем
файлам + личная перепроверка критичных), проверены XSS-векторы, SSRF, гонки, лимитер логина.

## 1. Что проверено и ПОДТВЕРЖДЕНО сильным (правки не нужны)
1. **Файлы документов** (`/api/files/[kind]/[id]`): все 4 вида (document / directory / request-file /
   ticket-attachment) проверяют владельца (winnerId / carrierId автора / участник обращения), staff — все;
   отдаются с CSP, `nosniff`, `no-store`, не-медиа — только скачиванием. Паспорта/СТС утечь не должны.
2. **Скоупинг заявок**: всё через `loadRequestFor(id, viewer)` — перевозчик видит только PUBLISHED,
   свои победы и свои ставки; DRAFT скрыт. Проверено в action/files/documents/verify/bulk-assign.
3. **Гонки ставок**: дедлайн и пол ставки перепроверяются ВНУТРИ транзакции (`inTx` с ретраем на
   SQLITE_BUSY); `award` отвергнут явно (победитель только автоподведением, где `updateMany` с
   условием `status='PUBLISHED'` защищает от двойного подведения). Скачивание bestRate — в транзакции.
4. **Admin-роуты** (access/users/db/files/nn) — все под `requireUser('admin')` (+ пермиссии); защита
   «последнего админа» в users; settings — только logist/admin; reports — logist/admin + perm.
5. **1С-интеграция**: ключ только в заголовке X-API-Key (не в URL), сравнение через digest +
   `timingSafeEqual`; OPTIONS-префлайт без данных.
6. **Логин**: scrypt + timingSafeEqual + **лимитер уже есть** — 8 неудачных попыток / 15 минут
   (MAX_FAILS/LOCK_MS в login-роуте, 429 при срабатывании). Раннее подозрение про брутфорс снято.
7. **XSS**: `dangerouslySetInnerHTML` нет нигде, кроме стандартного shadcn chart (конфиг из кода);
   пользовательские строки рендерит React (экранирование по умолчанию).
8. **SSRF**: map-tile проксирует ТОЛЬКО фиксированный tile.openstreetmap.org с валидацией z/x/y;
   пользовательские хосты в fetch не попадают.
9. notifications (userId=auth.id), support (автор/компания через canAccessTicket), platform-log/client
   (требует сессию — не открыта для спама), session version `sv` проверяется по БД для HTTP.

   в результате поля паспорта/СТС (мягкий IDOR: jobId — UUIDv4, TTL 15 мин, но данные персональные).

   «не найдена» чужому не-staff; владельцы переданы во всех 3 местах создания (drivers/intake,
