# Интеграция с 1С: черновики заявок из 1С

Двусторонняя схема:

1. **1С → платформа.** Кнопка в документе 1С отправляет `POST /api/integration/1c/requests`, и на платформе появляется **черновик** заявки (`DRAFT`) с автором «1С (интеграция)».
2. **Логист** видит его в «Черновиках заявок», при необходимости правит, задаёт срок торгов и публикует.
3. **Платформа → 1С.** 1С забирает статус, победителя, ставку и экипаж: `GET /api/integration/1c/requests?onecRef=…` (или весь реестр через `?since=`).
4. **ЭТрН.** 1С подтверждает накладную через `POST /api/integration/1c/etrn`, как и раньше.

## Что в этой папке

Всё по интеграции с 1С, кроме кода самой платформы:

| Файл | Назначение |
|---|---|
| `README.md` | Этот файл: схема обмена, поля, ответы, развёртывание. |
| `orders-form-web-logistic.bsl` | Модуль формы «Заказы грузоотправителей»: кнопка «в Веб-Логистик» рядом с «Путевые листы» — отмеченные рейсы черновиками на платформу, статусы и перевозчик обратно в рейсы. |
| `send-request-form-module.bsl` | Модуль формы отдельного документа «Заявка на перевозку» (если заявки ведутся документами). |
| `onec-check.mjs` | Проверка обмена с сервера или своего компьютера, без 1С и браузера. |
| `simulator/index.html` | Симулятор формы «Заказы грузоотправителей» с кнопкой «в Веб-Логистик» — для демонстрации в браузере. |
| `simulator/instructions.md` | Публикация симулятора на GitHub Pages и сценарий показа. |

Код платформы лежит там, где его ищет Next.js:

- `src/app/api/integration/1c/` — методы обмена;
- `src/lib/onec.ts` — ключ и CORS;
- `prisma/schema.prisma` — поле `Request.onecRef`.

Авторизация — заголовок `X-API-Key` со значением `ONEC_API_KEY` из `.env` сервера (не короче 24 символов). Без переменной все маршруты `/api/integration/1c/*` отвечают `503`.

Показать обмен без 1С можно в браузере: HTML-симулятор формы 1С [`simulator/index.html`](simulator/index.html) публикуется на GitHub Pages (инструкция — [`simulator/instructions.md`](simulator/instructions.md)).

## Переменные окружения

| Переменная | Обязательна | Значение |
|---|---|---|
| `ONEC_API_KEY` | да | Ключ интеграции, не короче 24 символов: `openssl rand -hex 24`. Тот же ключ — в модуле 1С и в симуляторе. |
| `ONEC_CORS_ORIGINS` | для симулятора | Сайты, которым браузер разрешит обращаться к `/ping` и `/requests`, через запятую: `https://vacantrix.github.io`. `*` — любой сайт, только для временной проверки. Пусто — CORS выключен; 1С это не мешает, она ходит с сервера. |
| `DATABASE_URL` | да | Как и раньше. После обновления — `bun run db:push`. |

## POST /api/integration/1c/requests

```json
{
  "oneC_number": "ЗП-0012 от 28.10.2026",
  "fromPoint": "Краснодарский край, г. Абинск, ул. Промышленная, д. 4",
  "toPoint": "г. Санкт-Петербург, Канонерский остров, д. 45",
  "cargo": "Перевозка готовой продукции - арматура",
  "tonnage": 20.5,
  "truckType": "Борт",
  "loadDate": "2026-10-30",
  "loadWindow": "09:00–18:00",
  "startRate": 4200,
  "mode": "AUCTION",
  "comment": "Срочная доставка"
}
```

| Поле | Обяз. | Что принимается |
|---|---|---|
| `oneC_number` | да | Ключ документа 1С, до 100 символов. Номера 1С повторяются каждый год, поэтому модуль формы шлёт «номер от даты». Повтор с тем же ключом **не создаёт дубль**. |
| `fromPoint`, `toPoint` | да | Адреса текстом, до 300 символов. Сохраняются как есть, со справочником точек не сводятся; для карты город берётся из адреса («Краснодарский край, г. Абинск, ул. Промышленная, 4» → Абинск), сам адрес показывается целиком. |
| `cargo` | да | Наименование груза. Сравнивается со справочником грузов без учёта регистра, «ё» и вида тире. Если такого груза нет, он **добавляется в справочник** (в ответе `cargoCreated: true`, запись в журнале событий). |
| `loadDate` | да | `ГГГГ-ММ-ДД`, `ГГГГ-ММ-ДДTчч:мм:сс` (так `ЗаписатьJSON` пишет тип Дата) или `ДД.ММ.ГГГГ`. Прошедшая дата отклоняется. |
| `tonnage` | нет | Тонны, `0 < x ≤ 200`. По умолчанию 20. |
| `truckType` | нет | `Тент` или `Борт` (регистр не важен). По умолчанию берётся из карточки груза. |
| `loadWindow` | нет | Строка до 40 символов. По умолчанию `08:00–12:00`. |
| `startRate` | нет | **₽ за тонну**, а не за рейс. `0` или не передавать: ставку задаст логист при публикации. |
| `mode` | нет | `AUCTION` (по умолчанию) или `CLOSED`. |
| `comment` | нет | До 1000 символов. Показывается исполнителю. |

Ответы:

| Код | Когда | Тело |
|---|---|---|
| `201` | черновик создан | `{ ok: true, data: { id, number, onecRef, status: "DRAFT", statusRu, cargo, createdAt, duplicate: false, cargoCreated } }` |
| `200` | документ уже отправлялся | то же, `duplicate: true` (данные первой отправки, черновик не меняется) |
| `400` | ошибка в данных | `{ ok: false, error: "понятный текст" }` |
| `401` / `503` | неверный ключ / интеграция выключена | `{ ok: false, error }` |

Номер заявки (`Z-<n>`) выдаёт платформа по своему правилу. Номер 1С хранится отдельно, в поле `Request.onecRef`.

### Примеры curl

Успешное создание (`201`) и повтор того же документа (`200`, `duplicate: true`):

```bash
curl -i -X POST https://<домен>/api/integration/1c/requests \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <ONEC_API_KEY>" \
  -d '{"oneC_number":"ЗП-00001 от 28.10.2026","fromPoint":"Москва, ул. Заводская, 1","toPoint":"Санкт-Петербург, пр. Ленина, 100","cargo":"Перевозка готовой продукции - арматура","tonnage":20,"truckType":"Тент","loadDate":"2026-11-02","loadWindow":"09:00–18:00","startRate":8400,"comment":"Срочная"}'
```

Ошибка в данных (`400`, `{"ok":false,"error":"Укажите fromPoint и toPoint — адреса погрузки и выгрузки"}`):

```bash
curl -i -X POST https://<домен>/api/integration/1c/requests \
  -H "Content-Type: application/json" -H "X-API-Key: <ONEC_API_KEY>" \
  -d '{"oneC_number":"ЗП-00002 от 28.10.2026","cargo":"Перевозка металлолома","loadDate":"2026-11-02"}'
```

Статус документа и предварительный запрос браузера (CORS):

```bash
curl -s -G https://<домен>/api/integration/1c/requests -H "X-API-Key: <ONEC_API_KEY>" --data-urlencode "onecRef=ЗП-00001 от 28.10.2026"
```

```bash
curl -i -X OPTIONS https://<домен>/api/integration/1c/requests -H "Origin: https://vacantrix.github.io" -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type,x-api-key"
```

## GET /api/integration/1c/requests?onecRef=…

Статус одного документа 1С: `data[0].status` / `statusRu`, `winner` (перевозчик и ИНН), `rates.best`, `crew` (водитель, ТС, прицеп), `etrn`. Поле `onecRef` есть у каждой строки реестра, так что 1С может сопоставлять и при выгрузке через `?since=`.

## Развёртывание на сервере

1. Подтянуть изменения и обновить схему БД: добавится одна необязательная колонка `Request.onecRef` с уникальным индексом, существующие данные не меняются.

   ```bash
   bun run db:push
   ```

2. Задать переменные в `.env` (ключ можно сгенерировать командой `openssl rand -hex 24`):

   ```
   ONEC_API_KEY=<ключ не короче 24 символов>
   ONEC_CORS_ORIGINS=https://vacantrix.github.io
   ```

   `ONEC_CORS_ORIGINS` нужна только для симулятора.

3. Пересобрать и перезапустить платформу (`bun run build`, затем перезапуск сервиса).
4. Проверить обмен **без 1С** (ключ — тот же, что на сервере):

   ```bash
   ONEC_URL=https://<домен-платформы> ONEC_API_KEY=<ключ> node docs/1c/onec-check.mjs
   ```

   Скрипт делает те же запросы, что модуль 1С: проверку связи, создание черновика, повтор (дубля быть не должно) и чтение статуса. Каждый запуск создаёт черновик «ПРОВЕРКА-…», логист удаляет его в «Черновиках заявок».

Caddy (`Caddyfile`) пропускает все пути, кроме `?XTransformPort=…`, на Next.js `:3000`, так что `/api/integration/1c/*` доступен снаружи без правок.

## Подключение в 1С

### Кнопка «в Веб-Логистик» в форме «Заказы грузоотправителей»

Модуль: [`orders-form-web-logistic.bsl`](orders-form-web-logistic.bsl).

1. Создайте в форме две команды:
   - **«ВВебЛогистик»** — поставьте в командную панель таблицы рейсов сразу после «Путевые листы»;
   - **«ОбновитьСтатусыВебЛогистик»** — в подменю «Еще» той же панели.
2. Добавьте в таблицу рейсов колонку `ВебЛогистик` (строка, 100).
3. Сверьте имена таблицы и колонок в `ИмяТаблицыРейсов()` и `КолонкиРейсов()`.
4. Укажите домен и ключ в `АдресПлатформы()` и `КлючAPI()`.

Как работает:

- **Рейс** — одна машина. Вес — сумма строк продукции рейса, груз определяется по номенклатуре («Перевозка готовой продукции - пруток / проволока / моток / катанка / арматура»).
- **Ключ на платформе** — «Рейс №N от ДД.ММ.ГГГГ», поэтому повторная отправка дубль не создаёт.
- **Обновление статусов** переносит в рейс перевозчика, выбранного на платформе, и его экипаж. Поля, которые уже заполнены в 1С, не затираются.

### Отдельный документ «Заявка на перевозку»

Модуль формы: [`send-request-form-module.bsl`](send-request-form-module.bsl) — если заявки ведутся отдельными документами.

1. В форме документа создайте команды **«ОтправитьНаПлатформу»** и **«СтатусНаПлатформе»** и вынесите их кнопками.
2. Скопируйте модуль. В функции `ДанныеЗаявкиДляПлатформы()` сверьте имена реквизитов документа со своими.
3. В `АдресПлатформы()` и `КлючAPI()` укажите домен и ключ (в рабочей базе — через константы).

Что учтено в модуле:

- запросы выполняются на сервере: ключ не уходит на клиент, код работает и в веб-клиенте;
- несохранённый документ сначала записывается, потому что номер присваивается при записи;
- повторное нажатие не создаёт дубль: платформа отвечает `200`, и 1С сообщает, что документ уже отправлен;
- сертификат сервера проверяется по корневым сертификатам ОС (`СертификатыУдостоверяющихЦентровОС`);
- тело уходит в UTF-8 без BOM; ответ читается в `Соответствие`, чтобы ключи вроде `to` не ломали `ПрочитатьJSON`.
