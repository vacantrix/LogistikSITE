# ПРОМТ: веб-платформа «Контур 1С» — эмулятор 1С для приложения водителя

> Готовый промт для рабочей сессии, которая создаст платформу с нуля.
> Вставь всё содержимое этого файла как первое сообщение сессии.

---

## 0. Контекст

Компания «АЗМЗ Логистика» строит **приложение водителя** для грузового автотранспортного предприятия (РФ, парк 100–500 ТС, требования 152-ФЗ о персональных данных). Приложение уже существует как веб-демо на Next.js и как Android-каркас; его ядро — офлайн-first протокол синхронизации с сервером.

Целевой поток: **сбыт формирует заявки в 1С → диспетчерская назначает ТС и водителя из числа доступных и готовых → водитель получает заявку в приложении → предрейсовая фотофиксация → рейс с навигацией → завершение**.

Проблема: рабочая конфигурация 1С заказчика содержит чувствительные данные и недоступна во внешней среде разработки. Нужен **эмулятор 1С** — промежуточная веб-платформа, через которую поток «из 1С в приложение водителя» проверяется целиком.

## 1. Что построить

Отдельное веб-приложение **«Контур 1С»** (Next.js, порт 3001), которое:

1. **Архитектурно повторяет 1С**: справочники, документы с нумерацией и проведением, статусная модель, регистры, журнал регистрации, план обмена (синхронизация). Не внешний вид 1С, а механика.
2. Даёт **рабочие места офиса**: экраны сбыта (создание заявок) и диспетчерской (назначение ТС + водителя, отмена, чат, реестр рейсов).
3. Публикует **те же интеграционные контракты, которые уже потребляет приложение водителя** — это главное. При подключении реальной 1С слой эмуляции подменяется коннектором, контракты и клиент не меняются.

Два API-слоя (разносить сознательно):

- `/api/1c/*` — «HTTP-сервис 1С»: то, что в проде публикует настоящая 1С (список заявок водителю, обратный канал статусов).
- `/api/driver/v1/*` — шина приложения: протокол синхронизации каркаса (pull/push/marks) + канал пробок.

За образец архитектуры взята типовая 1С:УАТ: документ «Заказ на ТС» (регистрация предварительных заявок на перевозку, планирование использования ТС) → «Рейс» → «Путевой лист»; статусы устанавливаются при проведении документов; закрытие заказа — по причине из справочника.

## 2. Стек и структура

- Next.js 16 (App Router, Route Handlers) + TypeScript

- Отдельный origin (порт 3001); CORS для источника приложения водителя (env `DRIVER_APP_ORIGIN`, в демо `*`)

## 4. Статусная модель заявки

```
NEW → DISPATCH → ASSIGNED → ACCEPTED → PRETRIP → IN_PROGRESS → DONE
                    ↑(из DISPATCH)                ↘ CANCELLED (только диспетчером, с причиной)
```

| Статус | Смысл | Кто переводит | Побочные эффекты |
|---|---|---|---|
| NEW | заведена сбытом | логист | номер из нумератора, запись в RegistrationLog |
| DISPATCH | в диспетчерской | авто | попадает в пул назначения |
| ASSIGNED | назначена ТС+водителю | диспетчер | **рождение Рейса** (раздел 5) + SyncJournal + SystemNote |
| ACCEPTED | водитель взял | водитель (ACCEPT) | видно в реестре офиса |
| PRETRIP | предрейсовая подготовка | водитель (PRETRIP_STEP) | журнал шагов фотофиксации |
| IN_PROGRESS | в пути | водитель (START_ROUTE) | TripEvent DEPARTURE |
| DONE | выполнена | водитель (COMPLETE_TRIP) | TripEvent TRIP_DONE, закрытие интервалов |
| CANCELLED | отменена | диспетчер | причина, SystemNote водителю |

Маппинг в упрощённые статусы приложения водителя (`Order1C.status`):

| Внутренний | Order1C.status |
|---|---|
| NEW, DISPATCH | `DISPATCH` |
| ASSIGNED, ACCEPTED, PRETRIP | `ASSIGNED` |
| DONE | `DONE` |
| CANCELLED | не возвращается (водителю придёт SystemNote) |

## 5. Бизнес-правила

### 5.1. Нумератор (как нумерация документов 1С)

Формат `ЗК-ГГГГ/NNNN` (например `ЗК-2026/1067`), годовой период, счётчик без пропусков. Атомарно (транзакция или `SELECT … FOR UPDATE`-аналог), номера уникальны при параллельном создании.

### 5.2. Проведение при назначении (валидации)

Назначение разрешено, только если:

1. `Vehicle.readiness = ready`;
2. `weightT` заявки ≤ `capacityT` ТС;
3. тип кузова совместим с грузом (справочная матрица: `tarp → металлоконструкции, паллеты`; `fridge → продукты`; и т.д. — достаточно маленькой таблицы в коде);
4. водитель активен и не занят в другом незавершённом рейсе;
5. заявка в статусе `DISPATCH`.

Нарушение → отказ с текстом причины (аналог «документ не проведён»), запись в RegistrationLog с уровнем `warning`.

### 5.3. Рождение рейса — одна транзакция (критично!)

`POST /api/office/requests/:id/assign` в **одной транзакции БД**:

1. валидации (5.2);
2. заявка → `ASSIGNED` + StatusHistory;
3. создать/обновить `Trip` (`tripCode = number` заявки, `status = assigned`, `driverId`, `vehicleId`);
4. создать `TripPoint`-ы: `loading` (fromLocation) и `unloading` (toLocation);
5. маршрут: вызвать 2ГИС Routing API через серверный прокси (ключ в env `GIS2_API_KEY`, `transport: 'truck'`, `traffic_mode: 'jam'`); при недоступности — заглушка (прямая между пунктами, время по 60 км/ч). Роутинг **не блокирует** транзакцию: сначала назначение с заглушкой, пересчёт фоном;
6. записи в `SyncJournal` для водителя: `TRIP` (UPSERT) и обе `TRIP_POINT` (UPSERT) — **снимки полей в формате раздела 6.3**;
7. `SystemNote` `ORDER_ASSIGNED` («Вам назначена заявка ЗК-2026/1071…») → тоже в SyncJournal.

Если записи SyncJournal не появятся в той же транзакции — водитель не увидит назначение. Это главная проверка фазы шины.

### 5.4. Действия водителя (обратный канал)

- `ACCEPT`: заявка назначена этому водителю → `ACCEPTED` + StatusHistory.
- `PRETRIP_STEP` (+ stepId): создать `PreTripInspection` при первом шаге, добавить `PreTripStep`. stepId обязателен и один из: `veh_side`, `veh_front`, `veh_rear`, `order_docs`, `lic`, `passport`.
- `START_ROUTE`: **отклонить с причиной «предрейсовый осмотр не завершён»**, пока не записаны все 6 шагов. Иначе: заявка → `IN_PROGRESS`, создать `TripEvent` `DEPARTURE` (source: MANUAL) и пересчитать автостатусы рейса (`lastEventType/At`, `status = in_progress`), всё в journal.
- `COMPLETE_TRIP`: `TripEvent` `TRIP_DONE`, закрыть открытые интервалы, `status = completed`, заявка → `DONE`.
- `ASSIGN` в обратном канале запрещён — назначение только из офиса.

## 6. API-контракты (эквивалентность 1:1 обязательна)

Общие правила: JSON; время — **epoch millis** (Long); идентификаторы — UUID-строки; водитель — заголовок `X-Driver-Id` (в демо необязателен — дефолтный водитель из сида); идемпотентность на уникальных ключах (`ON CONFLICT DO NOTHING`); `Cache-Control: no-store`.

### 6.2. POST /api/1c/orders — обратный канал

```json
// запрос
{ "orderId": "ЗК-2026/1067", "action": "PRETRIP_STEP", "stepId": "veh_side", "at": "2026-11-11T09:15:00.000Z", "photoDataUrl": null }
// ответ
{ "ok": true, "received": { "at": "…", "orderId": "ЗК-2026/1067", "action": "PRETRIP_STEP", "stepId": "veh_side" } }
```

- `action`: `ACCEPT` | `PRETRIP_STEP` | `START_ROUTE` | `COMPLETE_TRIP` (правила — 5.4).
- 400 с `{ "ok": false, "error": "…" }` при некорректном теле; 404 если заявка не найдена; 409 если START_ROUTE до завершения осмотра.
- `photoDataUrl` (base64 data-URL) — опционально: сохранить файл, записать `photoUrl` в PreTripStep.

- entity: `TRIP | TRIP_POINT | TRIP_EVENT | CHAT_MESSAGE | SYSTEM_NOTE`; op: `UPSERT | DELETE`.
- payload — снимок строки: **camelCase, epoch millis**, поля как у DTO каркаса (TripSnapshot: id, tripCode, status, driverId, vehicleId, plannedStartAt, plannedFinishAt, routeGeoJson, routeStepsJson, routeDistanceM, routeDurationS, routeMinLat/MinLon/MaxLat/MaxLon, lastEventType, lastEventAt; TripPointSnapshot: id, tripId, seqNo, kind, name, address, lat, lon, geofenceRadiusM, plannedArrivalAt, plannedDepartureAt; и т.д.).
- Дельта по `seq` (курсор = последний полученный), страницы по `limit`.

**POST /api/driver/v1/sync/push**

```json
// запрос
{ "deviceId": "…", "operations": [ { "opId": "<uuid>", "type": "TRIP_EVENT_CREATE", "payload": { "id": "<uuid>", "tripId": "…", "tripPointId": null, "vehicleId": "…", "deviceId": null, "type": "DEPARTURE", "occurredAt": 1730000000000, "source": "MANUAL", "lat": null, "lon": null, "note": null } } ] }
// ответ
{ "results": [ { "opId": "<uuid>", "status": "APPLIED" } ] }
```

- типы: `TRIP_EVENT_CREATE | MARK_PUBLISH | MARK_VOTE | CHAT_SEND | NOTE_READ`;
- статусы: `APPLIED | DUPLICATE | REJECTED`; `REJECTED` финален — `rejectReason` показывается водителю (например `MARK_EXPIRED`, `RATE_LIMIT`);
- применённая операция **обязательно** пишет снимок сущности в SyncJournal (иначе водитель не увидит собственное событие на другом устройстве);
- TripEvent: авто-закрытие интервалов (новое событие закрывает открытую «открывашку»), автостатусы рейса (`DEPARTURE → in_progress`, `TRIP_DONE → completed`, пересчёт `lastEventType/At`).

**GET /api/driver/v1/sync/marks?minLat&minLon&maxLat&maxLon&since**

```json
{ "snapshotAt": 1730000123456, "marks": [ { "id": "…", "category": "POTHOLE", "geometry": "{…LineString…}", "comment": null, "ttlHours": 6, "confirmCount": 3, "outdatedCount": 0, "createdAt": 1730000000000, "expiresAt": 1730021600000 } ] }
```

Активные (не истёкшие) пометки в bbox; автор не хранится.

**GET /api/driver/v1/traffic?minLat&minLon&maxLat&maxLon&since**

```json
{ "snapshotAt": 1730000123456, "segments": [ { "id": "osm:way:123:0", "title": "А-146 · Гайдук", "geometry": "{…LineString…}", "level": 2, "speedKmh": 27, "onRoute": true, "updatedAt": 1730000100000 } ] }
```

В демо — генератор правдоподобных сегментов (5–8 отрезков на дорогах Краснодарского края, случайный level 1–10).

## 10. Алгоритм работы (выполняй по фазам, каждая с критерием)

**Фаза 0 — каркас.** Инициализация Next.js + TS + Tailwind + shadcn/ui; `prisma/schema.prisma` целиком (раздел 3); сид (раздел 8). *Критерий:* `npm run dev` поднимается, сид создаёт справочники и заявки.

**Фаза 1 — ядро «1С».** Нумератор `ЗК-ГГГГ/NNNN`; RegistrationLog (писать из каждого сервиса); CRUD справочников + `/api/office/catalog/*`; документ TransportRequest: создание через API и UI, StatusHistory при каждом переходе. *Критерий:* заявка создаётся, статусы и журнал пишутся, нумерация без пропусков при 10 параллельных созданиях.

**Фаза 2 — диспетчеризация.** Экран «Диспетчерская»; подбор ТС по правилам 5.2 (бейджи причин негодности); `assign` = рождение рейса одной транзакцией (5.3, включая SyncJournal и SystemNote); `cancel` с причиной. *Критерий:* после назначения в БД есть trip, 2 точки, записи журнала; нарушение правил даёт отказ с причиной.

**Фаза 3 — шина.** `/api/driver/v1/sync/pull|push` с appliers (TRIP_EVENT_CREATE с авто-закрытием интервалов и автостатусами, MARK_PUBLISH, MARK_VOTE, CHAT_SEND, NOTE_READ), `marks`, `traffic`-генератор; `/api/1c/orders` GET/POST с маппингом статусов и логикой 5.4. *Критерий:* curl-прогон сценария 10.1 (шаги 1, 3–9) проходит.

**Фаза 4 — UI офиса.** Дашборд, Заявки, Реестр рейсов, Чат, Справочники, Журнал, Демо-панель. *Критерий:* весь сценарий проходится из браузера без curl.

**Фаза 5 — проверка и документация.** Подключение приложения водителя (10.2), README с запуском/сидом/curl-примерами, `.env.example` (`DATABASE_URL`, `GIS2_API_KEY`, `DRIVER_APP_ORIGIN`, `PORT=3001`). *Критерий:* приложение водителя проходит поток заявки без правок кода.

## 10.1. Сквозной сценарий приёмки

1. `curl localhost:3001/api/1c/orders` → 3 заявки, формат поле-в-поле как в 6.1.
2. В UI создать заявку → появилась в «Диспетчерской» со статусом DISPATCH.
3. Назначить ЗК-2026/1071 (КАМАЗ 5490, водитель №2) → в БД: ASSIGNED + trip + 2 точки + SyncJournal (TRIP, TRIP_POINT ×2) + SystemNote.
4. `curl -H 'X-Driver-Id: <водитель2>' 'localhost:3001/api/driver/v1/sync/pull?cursor=0'` → записи шага 3.
5. `POST /api/1c/orders {orderId: "ЗК-2026/1071", action: "ACCEPT"}` → в офисе статус ACCEPTED.
6. 6 × `PRETRIP_STEP` (`veh_side`…`passport`) → осмотр заполняется; `START_ROUTE` до завершения → **409 с причиной**.
7. `START_ROUTE` → TripEvent DEPARTURE, заявка IN_PROGRESS, рейс in_progress.
8. `COMPLETE_TRIP` → TripEvent TRIP_DONE, интервалы закрыты, заявка DONE.
9. Диспетчер пишет в чат → pull доставляет CHAT_MESSAGE.
10. Отмена диспетчером новой заявки → SystemNote водителю.

## 10.2. Подключение приложения водителя (финальный шаг интеграции)

В приложении водителя его собственный `/api/1c/orders` превращается в тонкий прокси (единственная правка):

```ts
// src/app/api/1c/orders/route.ts (приложение водителя)
const BASE = process.env.KONTUR_1C_URL ?? 'http://localhost:3001'

export async function GET(req: Request) {
  const r = await fetch(`${BASE}/api/1c/orders`, {
    headers: { 'X-Driver-Id': req.headers.get('x-driver-id') ?? '' },
    cache: 'no-store',
  })
  return new Response(r.body, { status: r.status, headers: { 'Content-Type': 'application/json' } })
}
// POST — аналогично, проксирует тело как есть.
```

Синхро-каналы приложения переключаются на `BASE` тем же способом. Ничего больше в клиенте не меняется — в этом смысл платформы.
