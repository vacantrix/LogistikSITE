# АЗМЗ Логистика · Каркас приложения водителя (п.1 плана работ)

Стартовый репозиторий каркаса: схема данных, скелет бэкенда (Kotlin/Spring Boot,
модульный монолит) и скелет Android-приложения (Kotlin/Compose/Room/WorkManager).
Офлайн-first — конституция: Room — единственный источник правды для UI, исходящие —
только через outbox (UUID + идемпотентный apply), входящие — дельта по курсору.

**Состав:** `backend/` — Spring Boot + Flyway V1–V6 · `android/` — 9 Gradle-модулей ·
`docs/` — ER-диаграмма и схема потоков синхронизации · `docker-compose.yml`.

## 1. Решения, зафиксированные в рабочей сессии

| # | Развилка | Решение | Где в коде |
|---|----------|---------|------------|
| 1 | Объём первой итерации | Схема БД + скелеты приложения и бэкенда | весь репозиторий |
| 2 | Каналы синхронизации | Личный журнал водителя (oplog, монотонный seq) + отдельный гео-канал пометок (снимок по bbox коридора) | `V5__sync.sql`, `/sync/pull`, `/sync/marks`, `PullWorker` |
| 3 | Незакрытые интервалы | Авто-закрытие: следующее событие закрывает открытую открывашку (флаг `interval_auto_closed`); «Рейс завершён» закрывает всё | `TripEventApplier`, `TripEventRules`, `OutboxRepository.markTripEvent` |
| 4 | Правки событий (гибрид) | Ручные отметки (`MANUAL_BACKDATED`) офис правит может (`edited_*`); геозонные — только корректирующей записью (`correction_of`) | `trip_event`, `V3__events.sql` |
| 5 | Привязка устройств | Планшет закреплён за машиной (MDM), водитель логинится в смену; событие хранит `driver_id + vehicle_id + device_id` | `V1__reference.sql` |
| 6 | TTL пометок | TTL автора: 6 ч / 12 ч / 30 дней с момента применения на сервере, не продлевается; голоса влияют только на порядок показа | `road_mark.expires_at`, `MarkApplier` |
| 7 | Авторство пометок | Автора не храним вовсе; анти-спам — счётчик публикаций по аккаунту без привязки к пометке (минимизация ПДн) | `mark_publication_log` |
| 8 | Тайлы коридора | PMTiles: векторные тайлы из выгрузки OSM, качаем до z14, оверзум до z17, свой стиль в MapLibre | `PmtilesCorridorManager`, раздел «Тайлы» ниже |

Плюс три следствия, заложенные без вопроса (лицензии и железо):

- **Nominatim — только self-hosted** (публичный API не допускает продакшн-нагрузку
  по политике использования) — см. `docker-compose.yml`.
- **Пуши — только «будильник»**: FCM не работает без Google-сервисов (типично для
  MDM-парка), RuStore Push требует установленного RuStore; гарантированный уровень —
  периодический pull через WorkManager (15 мин) + внеочередной kick при возврате связи.
  Данные пуши не переносят.
- **Идемпотентность — на уникальности ключей** (`sync_operation.op_id`,
  клиентские UUID сущностей, `ON CONFLICT DO NOTHING`), а не на сравнении содержимого.

## 3. Схема данных (V1–V6)

| Таблица | Назначение |
|---|---|
| `driver`, `vehicle` | Справочники. **Интеграционная точка №1**: если контур персонала уже есть — репликация |
| `device` | Планшет в кабине, привязан к машине, `mdm_enrollment_id` (Headwind MDM) |
| `driver_shift` | Смена: кто за рулём в момент события |
| `trip` | Рейс (Z-xxxx): геометрия OSRM, манёвры `route_steps`, автостатусы `last_event_*` |
| `trip_point` | Точки маршрута с геозоной `geofence_radius_m` для смарт-карточек |
| `trip_event` | **Слой 1** — события рейса, клиентские UUID, интервальность на «открывашке» |
| `road_mark` | **Слой 2** — пометки «водители для водителей», PostGIS LineString, TTL автора, без автора |
| `mark_vote` | Голоса: дедупликация `(mark, voter)`, наружу — только счётчики |
| `mark_publication_log` | Анти-спам: факт публикации без ссылки на пометку |
| `sync_operation` | Идемпотентность push: `op_id` → статус (APPLIED/DUPLICATE/REJECTED) |
| `sync_journal` | **Канал 1**: личный oplog водителя (seq, entity, op, payload-снимок) |
| `chat_message`, `system_note` | Таб «Офис»: чат и «Заявка Z-1067 изменена офисом» |
| `position_ping` | Закладка под дашборд директора (фаза 5), best-effort, мимо outbox |

### Типы событий и пары

| Код | Название | Роль |
|---|---|---|
| `DEPARTURE` | Выезд | точечное |
| `ARRIVAL_LOADING` | Прибытие на погрузку | открывает «Погрузка» |
| `LOADING_DONE` | Погрузка завершена | закрывает «Погрузка» |
| `REST_START` | Начать стоянку по тахографу | открывает «Стоянка» |
| `REST_END` | Завершить стоянку | закрывает «Стоянку» |
| `ARRIVAL_UNLOADING` | Прибытие на выгрузку | открывает «Выгрузка» |
| `UNLOADING_DONE` | Выгрузка завершена | закрывает «Выгрузку» |
| `TRIP_DONE` | Рейс завершён | закрывает ВСЕ открытые интервалы |

Правила:

- **Источник отметки**: `GEOFENCE` (смарт-карточка) · `MANUAL` (кнопка) ·
  `MANUAL_BACKDATED` (кнопка + «Указать время», помечается «вручную»).
- **Авто-закрытие**: новое событие закрывает открытые открывашки старше себя;
  явная закрывашка → `interval_auto_closed = false`, иначе `true`.
  «Рейс завершён» закрывает всё (клампинг `GREATEST(occurred_at, ?)`).
- **Автостатусы реестра**: в той же транзакции пересчитываются
  `trip.last_event_type/at` и `status` (DEPARTURE → in_progress, TRIP_DONE → completed) —
  офис не звонит «где ты».
- Правила продублированы на клиенте (`TripEventRules`) и сервере (`TripEventApplier`).
  Это осознанный дубль каркаса; кандидат на общий KMP-модуль. Сервер — источник
  истины, клиент сходится к нему через upsert-ы журнала по id.

### Почему курсор — seq, а не время

`sync_journal.seq` — серверная монотонная последовательность. Часы водителя
(и даже NTP-скачок на сервере) не могут ни пропустить, ни задублировать дельту.
Курсор пометок (`snapshotAt`) — тоже серверное время снимка.

## 4. Протокол синхронизации

### Канал 1 — личный журнал (pull)

```
GET /api/driver/v1/sync/pull?cursor=42&limit=500
→ { "entries": [ { "seq": 43, "entity": "TRIP_EVENT", "op": "UPSERT",
                   "payload": { …снимок строки, camelCase, epoch millis… } } ],
    "cursor": 43, "hasMore": false }
```

Клиент применяет upsert/delete по id (идемпотентно), курсор сохраняет после
каждой страницы — обрыв связи на середине не заставляет качать заново.

### Сброс очереди (push)

```
POST /api/driver/v1/sync/push
{ "deviceId": "…", "operations": [
    { "opId": "<uuid>", "type": "TRIP_EVENT_CREATE", "payload": { … } } ] }
→ { "results": [ { "opId": "<uuid>", "status": "APPLIED" } ] }
```

- `APPLIED` / `DUPLICATE` → операция закрыта в outbox;
- `REJECTED` — финален (`RATE_LIMIT`, `MARK_EXPIRED`, …), причина показывается
  пользователю, повторов нет;
- сеть/5xx → `Result.retry()` с экспоненциальным backoff.

### Канал 2 — пометки (снимок по bbox)

```
GET /api/driver/v1/sync/marks?minLat=54&minLon=37&maxLat=56&maxLon=38&since=1730000000000
→ { "snapshotAt": 1730000123456, "marks": [ … ] }
```

Пометки не фан-аутятся в личные журналы: каждый клиент тянет активные в bbox
коридора своего рейса. Истёкшие чистятся локально по `expiresAt`. Голос меняет
`updated_at` → пометка приедет в следующем снимке. NB: при рейсах за 180°
(Чукотка) клиент присылает два bbox.

## 5. Интеграционные точки с существующей платформой

1. **Персонал и автопарк** (`driver`, `vehicle`) — реплицировать из контура
   платформы или заменить на ссылки.
2. **Рождение рейса**: заявка/тендер → `trip` + `trip_point` + `route_steps`
   (вызов OSRM). Обязан писать `SyncJournalWriter.upsert(driverId, "TRIP", …)`
   в той же транзакции — иначе водитель не увидит назначение.
3. **Офисные события** (чат диспетчера, «заявка изменена», отмена рейса) —
   аналогично через `SyncJournalWriter` (`CHAT_MESSAGE`, `SYSTEM_NOTE`).
   Рекомендация: явные вызовы из офисных модулей; CDC/триггеры — позже, если
   начнут забывать.
4. **Реестр рейсов офиса**: читает `trip.last_event_*`, `status` и вьюху
   `v_open_interval` (незакрытые интервалы для разбора диспетчером).
5. **ЭДО/ЭТрН не затрагиваются** — раздела «Документы» в приложении нет.
6. **Дашборд директора** (фаза 5): срез парка из событий (Выезд → в движении,
   ARRIVAL_* → на погрузке/выгрузке, REST_START → на стоянке по тахографу),
   уточнение — `position_ping`.

## 6. Запуск локально

### Бэкенд

```bash
docker compose up -d postgres
cd backend && ./gradlew bootRun --args='--spring.profiles.active=demo'
```

`DemoDataRunner` создаст водителя, машину, рейс Z-1001 (Химки → Тула) и напечатает
готовые curl-примеры с реальными id. Проверка:

```bash
curl -H "X-Driver-Id: <из лога>" 'http://localhost:8080/api/driver/v1/sync/pull?cursor=0'
curl -X POST -H 'Content-Type: application/json' -H 'X-Driver-Id: <из лога>' \
  -d '{"deviceId":null,"operations":[{"opId":"<uuid>","type":"TRIP_EVENT_CREATE","payload":{"id":"<uuid>","tripId":"<из лога>","tripPointId":null,"vehicleId":"<из лога>","deviceId":null,"type":"DEPARTURE","occurredAt":1730000000000,"source":"MANUAL","lat":null,"lon":null,"note":"демо"}}]}' \
  http://localhost:8080/api/driver/v1/sync/push
curl 'http://localhost:8080/api/driver/v1/sync/marks?minLat=54&minLon=37&maxLat=56&maxLon=38'
```

### Android

1. Открыть `android/` в Android Studio (сгенерировать Gradle wrapper: `gradle wrapper`
   или через IDE).
2. Запустить бэкенд с профилем `demo`, взять `driverId` из лога.
3. В каркасе водитель подставляется в `AppGraph.driverId` (например, одной строкой
   в `AzmzApplication.onCreate` после `AppGraph.init`): `AppGraph.driverId = "<uuid>"`.
   Это точка входа «логина в смену», который в п.2 заменит её на JWT.
4. Базовый URL — `http://10.0.2.2:8080/api/driver/v1/` (эмулятор → localhost),
   `AppGraph.DEFAULT_BASE_URL`.
5. Запустить на эмуляторе/устройстве: индикатор связи оживёт, табы «Рейс»/«История»
   покажут демо-рейс после pull.

### Версии зависимостей

Версии в `android/gradle/libs.versions.toml` ориентировочные — зафиксируйте
актуальные при первом билде (AGP/Kotlin/Compose BOM/Room/WorkManager/Retrofit/MapLibre).

## 7. Лицензии и 152-ФЗ

- **Яндекс**: платные API не используем; бесплатный API запрещён для закрытого
  продукта и диспетчеризации — не используем и его. Deep-link «Вести в Яндекс
  Навигаторе» (intent `yandexnavi://`) допустим — это не API.
- **OSM/ODbL**: обязательная атрибуция «© OpenStreetMap contributors» на экране
  карты (в style JSON и в «О настройках»). Собственная выгрузка РФ (Geofabrik)
  для OSRM/Nominatim/PMTiles.
- **Nominatim**: только self-hosted инстанс — публичный API по политике
  использования не допускает продакшн-нагрузку.
- **152-ФЗ**: ПДн (местоположение, чат) — только в облако РФ; `position_ping` —
  retention по политике (дефолт 90 дней, чистка джобой); согласия — в трудовом
  контракте. Пометки без автора — минимизация ПДн.
- **Тахограф СКЗИ**: файлы не расшифровываем сами — выгрузки через ИАЦ РАТ
  (карта — 28 дней, прибор — 365, приказ Минтранса №440). В каркасе тахограф
  не участвует; ручная загрузка диспетчером — п.4 плана.

## 8. Политика миграций (то, что «трудно исправить позже»)

- **Сервер**: только Flyway, миграции_append-only, никаких правок применённых файлов.
- **Клиент**: Room `exportSchema = true`, схемы коммитятся в
  `android/core/data/schemas/`. `fallbackToDestructiveMigration()` включён ТОЛЬКО
  на время каркаса — перед п.2 убрать и писать миграции.
- Каналы синхронизации расширяемы: новый тип entity в журнале — это новое значение
  `entity` + ветка в `applyEntries`; старые клиенты её игнорируют.

## 9. Тайлы (PMTiles-коридор)

1. Свой tile-сервер: выгрузка OSM РФ → PMTiles → `pmtiles serve` (или tileserver-gl),
   файлы в S3 (Yandex Object Storage).
2. Карта качает зумы до z14, MapLibre дорисовывает до z17 оверзумом — коридор
   межгорода укладывается в десятки МБ.
3. Коридор ≈ цепочка прямоугольных офлайн-регионов вдоль маршрута (запас ~10 км)
   через `OfflineManager.defineRegion` — контракт в `PmtilesCorridorManager`.
4. Манёвры (`trip.route_steps`) лежат в Room — навигация офлайн.
5. Чек-лист пилота «всё скачано» — `PmtilesCorridorManager.isCorridorReady`.

Альтернатива позже: прямой PMTiles-файл коридора в кэше (без сервера) — контракт
класса это допускает.

## 10. Открытые вопросы (не блокируют каркас)

1. Из какой сущности платформы рождается `trip` (заявка? тендер?) — интеграционная
   точка №2; нужен реальный источник статусов «assigned».
2. Шаг «принять рейс» водителем в брифе отсутствует — добавить ли?
3. Отмена рейса офисом: подтверждён ли сценарий `status='cancelled'` + `SYSTEM_NOTE`?
4. Лимиты анти-спама пометок: дефолт 10/час на водителя — вынести в конфиг.
5. Retention `position_ping` (дефолт 90 дней) и текст согласия на ПДн — юр. оформление.
6. Антимеридиан (Чукотка) для bbox-запросов пометок — сделать два bbox при появлении
   рейсов за 180°.
7. Пуш-провайдер на пилоте: RuStore Push при наличии RuStore на устройствах;
   поллинг WorkManager — гарантированный уровень в любом случае.
8. Дублирование правил событий (клиент/сервер) — вынести в общий KMP-модуль после п.2.
